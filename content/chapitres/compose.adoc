== 🏁🔢 Ordre de démarrage

L'ordre de démarrage fait référence à la séquence dans laquelle les services définis dans un fichier Docker Compose sont lancés.

[%auto-animate]
== 🏁🔢 Ordre de démarrage

[.title]
Pourquoi est-ce important ?
[%step]
Certains services peuvent dépendre d'autres services pour fonctionner correctement.
[%step]
Par exemple, une application web peut avoir besoin qu'une base de données soit opérationnelle avant de pouvoir démarrer.

[%auto-animate]
== 🏁🔢 Ordre de démarrage

[.title]
Comment Docker Compose gère-t-il l'ordre de démarrage ?
[%step]
Sans dépendance déclarée entre eux, Docker Compose démarre les services *en parallèle* : l'ordre dans lequel ils sont écrits dans le fichier ne compte pas.
[%step]
Cinq services écrits `zulu`, `alpha`, `mike`, `bravo`, `yankee`, cinq `docker compose up` : quatre ordres de démarrage différents, et un seul identique au fichier.

[.notes]
--
Mesuré avec Docker Compose 5.5.1 en comparant le `StartedAt` de chaque conteneur.
L'ordre ne suit le fichier que par hasard.
Ce qui impose une séquence : `depends_on`, et trois dépendances implicites, `links`, `volumes_from` et `network_mode: "service:..."`.
Mesuré aussi : avec chacune des trois, le service dont on dépend démarre en premier 5 fois sur 5, même écrit en second.
--

[%auto-animate]
== 🏁🔢 Ordre de démarrage

[.title]
Comment gérer les dépendances entre services ?
[%step]
Docker Compose offre deux directives pour gérer les dépendances entre services : `depends_on` et `healthcheck`.

[%step]
- `depends_on` : Cette directive peut être utilisée pour indiquer qu'un service dépend d'un autre service.
Cependant, cela ne garantit pas que le service dépendant sera prêt à être utilisé lorsque le service qui en dépend sera lancé.
- `healthcheck` : Cette directive peut être utilisée pour vérifier l'état de santé d'un service.
En combinaison avec `depends_on`, elle peut aider à s'assurer qu'un service est prêt à être utilisé avant de lancer les services qui en dépendent.

[%auto-animate]
== 🏁🔢 Ordre de démarrage

[.title]
Exemple
Voici un exemple de fichier Docker Compose qui utilise `depends_on` et `healthcheck` pour gérer l'ordre de démarrage des services :

[%step]
[source,yaml]
----
version: '3'
services:
  web:
    build: .
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 30s
      timeout: 30s
      retries: 3
----

[%step]
Dans cet exemple, le service web dépend du service db.
Le service db est vérifié toutes les 30 secondes pour s'assurer qu'il est prêt à être utilisé.
Le service web ne sera lancé que lorsque le service db sera en bonne santé.

[%auto-animate]
== 🏁🔢 Ordre de démarrage❓🤔 Conditions.

WARNING: Rappel:
La directive `depends_on` dans un fichier Docker Compose est utilisée pour indiquer qu'un service dépend d'un autre service.
Cela signifie que le service dépendant ne sera pas démarré tant que les services dont il dépend n'auront pas été démarrés.

[%auto-animate]
== 🏁🔢 Ordre de démarrage❓🤔 Autres conditions.

En plus de la condition service_healthy, il existe d'autres conditions que vous pouvez utiliser avec `depends_on`:
[%step]
`service_started` : Cette condition signifie que le service dépendant ne sera pas démarré tant que le service dont il dépend n'aura pas été démarré.
[%step]
`service_completed_successfully`: Cette condition indique qu'un service dépendant ne doit pas démarrer avant qu'un autre service ait terminé avec succès. Cela peut être utile dans des scénarios où un service doit effectuer une tâche unique qui doit être terminée avant que d'autres services puissent débuter.
[%step]
Cependant, cela ne garantit pas que le service dont il dépend est prêt à être utilisé.

[%auto-animate]
== 🏁🔢 Ordre de démarrage❓🤔 Autre condition.

Voici un exemple de comment vous pourriez utiliser `service_started` dans un fichier Docker Compose :
[%step]
[source,yaml]
----
version: '3'
services:
  web:
    build: .
    depends_on:
      db:
        condition: service_started
  db:
    image: postgres
----

[%step]
Dans cet exemple, le service `web` ne sera démarré que lorsque le service `db` aura été démarré.

[%auto-animate]
== 🏁🔢 Ordre de démarrage & 🩺✅ healthcheck

WARNING: Rappel
`healthcheck` est une instruction dans un `Dockerfile` qui permet de vérifier l'état de santé d'un service.
Il peut être utilisé pour déterminer si un service est prêt à être utilisé ou non.
[%step]
Voici un exemple de `healthcheck` dans un `Dockerfile` :
[%step]
[source,dockerfile]
----
FROM postgres
HEALTHCHECK --interval=5m --timeout=3s \
  CMD pg_isready -U postgres || exit 1
----
[%step]
Dans cet exemple, `pg_isready -U postgres` est la commande utilisée pour vérifier l'état de santé du service.
Si cette commande réussit, le service est considéré comme sain.
Sinon, il est considéré comme malsain.

[%auto-animate]

== 🏁🔢 🩺✅ Comment healthcheck et depends_on travaillent ensemble ?
[.title]
En combinant `healthcheck` et `depends_on`, vous pouvez contrôler l'ordre de démarrage des services en fonction de leur état de santé.
Par exemple, vous pouvez vous assurer qu'un service de base de données est prêt à être utilisé avant de démarrer une application web qui en dépend.

[%auto-animate]
== 🏁🔢 Ordre de démarrage 📊📝 Pour résumer

L'ordre de démarrage fait référence à la séquence dans laquelle les services définis dans un fichier Docker Compose sont lancés.
Sans dépendance déclarée (`depends_on`, mais aussi `links`, `volumes_from` ou `network_mode: "service:..."`), les services démarrent en parallèle, dans un ordre qui change d'un lancement à l'autre.

[%step]
Docker Compose offre deux directives pour gérer les dépendances entre services : `depends_on` et `healthcheck`.

[%auto-animate]
== 🏁🔢 Ordre de démarrage 📊📝 Pour résumer

- `depends_on` : Cette directive peut être utilisée pour indiquer qu'un service dépend d'un autre service. Elle peut être utilisée avec deux conditions : `service_started` et `service_healthy`.
- `service_started` : Cette condition signifie que le service dépendant ne sera pas démarré tant que le service dont il dépend n'aura pas été démarré. Cependant, cela ne garantit pas que le service dont il dépend est prêt à être utilisé.
- `service_healthy` : Cette condition est utilisée avec la directive healthcheck dans un Dockerfile pour vérifier l'état de santé d'un service. Si la commande healthcheck réussit, Docker considère le service comme sain. Sinon, il est considéré comme malsain.

[%auto-animate]
== 🏁🔢 Ordre de démarrage 📊📝 Pour résumer
[.title]
Exemple
Voici un exemple de fichier Docker Compose qui utilise depends_on et healthcheck pour gérer l'ordre de démarrage des services :
[%step]
[source,yaml]
----
version: '3'
services:
  web:
    build: .
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 30s
      timeout: 30s
      retries: 3
----

== 🏁🔢 Étude de cas 📚🔍

Un exemple de fichier docker-compose.yml utilisé dans Jenkins:

https://raw.githubusercontent.com/jenkins-docs/quickstart-tutorials/refs/heads/main/docker-compose.yaml

[source,yaml]
----
sidekick_service:
    # Configuration for the sidekick service
    image: ${DOCKERHUB_USERNAME}/jenkinsci-tutorials:sidekick_
    stdin_open: true
    tty: true
    entrypoint: sh -c "/usr/local/bin/keygen.sh /ssh-dir"  # Runs the keygen.sh script and specifies the output directory
    volumes:
      - agent-ssh-dir:/ssh-dir  # Mounts the agent-ssh-dir volume to the /ssh-dir path inside the container
    healthcheck:
      test: [ "CMD-SHELL", "[ -f /ssh-dir/conductor_ok ] || exit 1" ]  # Checks if the conductor_ok file exists in the /ssh-dir path
      interval: 5s
      timeout: 10s
      retries: 5
----
[%step]
Les options `stdin_open: true` et `tty: true` sont utilisées pour garder l'entrée standard du conteneur ouverte et pour allouer un pseudo-TTY au conteneur, respectivement.
C'est généralement fait lorsque vous voulez interagir avec le service en cours d'exécution.

== 🏁🔢 Étude de cas 📚🔍

[source,yaml]
----
sidekick_service:
    # Configuration for the sidekick service
    image: ${DOCKERHUB_USERNAME}/jenkinsci-tutorials:sidekick_
    stdin_open: true
    tty: true
    entrypoint: sh -c "/usr/local/bin/keygen.sh /ssh-dir"  # Runs the keygen.sh script and specifies the output directory
    volumes:
      - agent-ssh-dir:/ssh-dir  # Mounts the agent-ssh-dir volume to the /ssh-dir path inside the container
    healthcheck:
      test: [ "CMD-SHELL", "[ -f /ssh-dir/conductor_ok ] || exit 1" ]  # Checks if the conductor_ok file exists in the /ssh-dir path
      interval: 5s
      timeout: 10s
      retries: 5
----
[%step]
* Enfin, un healthcheck est défini pour le service. Il s'agit d'une commande que Docker exécutera à l'intérieur du conteneur pour vérifier sa santé.
* Dans ce cas, la commande vérifie si un fichier nommé `conductor_ok` existe dans le répertoire `/ssh-dir`.
* Si le fichier existe, la commande réussit et Docker considère le service comme sain.
* Si le fichier n'existe pas, la commande échoue et Docker considère le service comme malsain.
* Docker exécutera cette vérification de santé toutes les 5 secondes (`interval: 5s`), et si elle ne répond pas dans les 10 secondes (`timeout: 10s`), Docker la considérera comme un échec. Docker réessaiera une vérification de santé échouée 5 fois (`retries: 5`) avant de considérer le service comme malsain.

== ⚠️ Piège : Outils manquants dans les images de base

=== Le Problème

[IMPORTANT]
====
Si la commande utilisée dans un health check **n'existe pas dans l'image**, le health check **échouera** !
====

[%step]
* Les images **slim** et **alpine** sont **minimalistes** pour réduire la taille
* Elles **ne contiennent PAS** les outils courants (curl, wget, bash, etc.)
* Health check avec outil manquant → **Status "unhealthy"** → **Conteneur inutilisable**

| `alpine:3.19`

| `python:3.11`

**Images officielles de bases de données** (postgres, mysql, redis, mongodb) incluent généralement leurs propres outils de diagnostic.

=== Symptômes d'un Health Check avec Outil Manquant

Quand un health check échoue à cause d'un outil manquant :

[source,bash]
----
docker compose ps
----

[source,text]
----
NAME            IMAGE                  STATUS
myapp-backend   python:3.11-slim      Up 30 seconds (unhealthy)
----

[source,bash]
----
docker container inspect myapp-backend | grep -A 10 Health
----

[source,json]
----
"Health": {
    "Status": "unhealthy",
    "FailingStreak": 5,
    "Log": [
        {
            "ExitCode": 127,  # ← Code 127 = "Command not found"
            "Output": "/bin/sh: curl: not found"
        }
    ]
}
----

[WARNING]
====
**ExitCode 127** = La commande **n'existe pas** dans l'image !
====

=== Solution 1 : Installer l'Outil dans le Dockerfile

La méthode la plus fiable : **installer l'outil manquant**.

[source,dockerfile]
----
FROM python:3.11-slim

WORKDIR /app

# Installer curl pour le health check
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*  # ← Nettoyer le cache apt

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000

CMD ["python", "app.py"]
----

[source,yaml]
----
services:
  backend:
    build: ./backend
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]  # ✅ Fonctionne !
      interval: 10s
      timeout: 5s
      retries: 3
----

[TIP]
====
**Alpine** : Utiliser `apk add` au lieu de `apt-get`

[source,dockerfile]
----
FROM python:3.11-alpine

RUN apk add --no-cache curl
----
====

=== Solution 2 : Utiliser des Alternatives Natives

Utilisez les outils **déjà présents** dans l'image.

[cols="2,3,3", options="header"]
|===
| Besoin
| Au lieu de...
| Utiliser

| Tester connexion HTTP
| `curl http://localhost:8080`
| `wget --spider --quiet http://localhost:8080`

| Tester port ouvert
| `curl -f localhost:8080`
| `nc -z localhost 8080` (si netcat disponible) +
`cat < /dev/tcp/localhost/8080` (bash uniquement)

| Tester fichier existe
| `+curl -f http://...+`
| `[ -f /path/to/file ] \|\| exit 1`

| Tester processus
| `+curl http://...+`
| `ps aux \| grep "mon-process"`
|===

**Exemple avec wget** (disponible dans Alpine) :

[source,yaml]
----
services:
  frontend:
    image: node:18-alpine
    healthcheck:
      test: ["CMD-SHELL", "wget --no-verbose --tries=1 --spider http://localhost:3000 || exit 1"]
      interval: 30s
      timeout: 10s
      retries: 3
----

=== Solution 3 : Utiliser Python/Node Built-in

[NOTE]
====
Cette solution s'applique **uniquement** aux images qui contiennent déjà Python ou Node.js (ex: `python:3.11-slim`, `node:18-alpine`, images d'applications Python/Node). N'installez pas Python/Node.js juste pour le health check - utilisez plutôt les Solutions 1 ou 2.
====

**Health check avec Python** (pour images Python) :

[source,yaml]
----
services:
  backend:
    image: python:3.11-slim  # ← Déjà contient Python
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:5000/health')"]
      interval: 10s
      timeout: 5s
      retries: 3
----

**Health check avec Node.js** (pour images Node) :

[source,yaml]
----
services:
  api:
    image: node:18-alpine  # ← Déjà contient Node.js
    healthcheck:
      test: ["CMD", "node", "-e", "require('http').get('http://localhost:8080/health', (r) => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 3
----

=== 🎓 Exercice Pratique

Corrigez ce `docker-compose.yml` qui échoue avec "unhealthy" :

[source,yaml]
----
services:
  webapp:
    image: python:3.11-slim
    # Dockerfile n'installe PAS curl !
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 10s
----

**3 solutions possibles** :

1. Ajouter `RUN apt-get update && apt-get install -y curl` dans Dockerfile
2. Remplacer par `wget --spider --quiet http://localhost:5000/health`
3. Remplacer par health check Python natif (Solution 3)

=== 📊 En Résumé (Checklist)

Avant d'écrire un health check :

[%step]
1. ✅ **Vérifier** : La commande existe-t-elle dans l'image ?
2. ✅ **Tester** : `docker container run --rm image commande` pour vérifier
3. ✅ **Choisir une solution** :
   * Installer l'outil (Solution 1) → Recommandé pour production
   * Utiliser alternative native (Solution 2) → Léger, pas d'install
   * Utiliser Python/Node built-in (Solution 3) → Images avec runtime uniquement

[WARNING]
====
**Erreurs fréquentes** :

* ❌ `curl` dans `python:3.11-slim` → ExitCode 127
* ❌ `bash` dans Alpine → Utiliser `sh`
* ❌ Oublier `--no-cache` lors de l'install → Image plus lourde
====

[TIP]
====
**Règle d'or** : `docker container run --rm mon-image commande`

Si la commande échoue → Elle échouera aussi dans le health check !
====

== 🎓 Travaux pratiques #12-BIS 🔨🔥

[%step]
* Pour les services `gitlab-runner-1` et `gitlab-runner-2`, remplacez l'URL externe par une dépendance au service gitlab en ajoutant `depends_on:` sur une nouvelle ligne, puis `- gitlab` sur la ligne suivante.
* Montez le socket Docker et le fichier de configuration de GitLab Runner
[%step]
** en ajoutant `- '/var/run/docker.sock:/var/run/docker.sock'`
** et `- 'gitlab-runner-1-config:/etc/gitlab-runner'` (ou `- 'gitlab-runner-2-config:/etc/gitlab-runner'` pour `gitlab-runner-2`) sous `volumes:`.
[%step]
⚠️ Ce socket donne au runner le contrôle du moteur Docker de votre machine : c'est par lui qu'il lance un conteneur par job. Sur une machine partagée, ce n'est pas un montage anodin.

[.notes]
--
Monter `/var/run/docker.sock`, c'est la même prudence que le port 2375 vu au chapitre réseaux : qui parle au socket pilote le moteur, et peut lancer un conteneur qui monte la racine de l'hôte.
Docker le dit lui-même : « only trusted users should be allowed to control your Docker daemon » (https://docs.docker.com/engine/security/#docker-daemon-attack-surface).

Le socket ne sert qu'à l'exécuteur `docker`.
Mesuré le 2026-10-07 avec `gitlab/gitlab-runner:alpine-v19.5.1` : l'image n'a pas de client `docker`, c'est le runner lui-même qui appelle l'API du moteur pour créer les conteneurs des jobs, à côté du sien (pas de Docker-in-Docker).
Avec l'exécuteur `shell`, les jobs tournent dans le conteneur du runner et le socket ne sert à rien.
--

== 👤 Profils dans Docker Compose 🐙
On a vu déjà l'instruction `depends_on` dans un fichier Docker Compose.
[%step]
- Elle permet de définir des dépendances entre les services.
- Mais que faire si on veut définir un lot de services qui fonctionnent ensemble, sans pour autant être en interdépendance ?
- Les profils dans Docker Compose permettent de définir des groupes de services qui peuvent être activés ou désactivés ensemble.

  db:
    image: mon_image_db
  service_dev:
    image: mon_image_dev

      - dev

# service_dev

[.small%step]

== 🧩 Profils ou fichiers override ?

[source,bash]
----
# compose.yml et compose.override.yml sont fusionnés automatiquement
docker compose up -d
# en production, on choisit les fichiers explicitement
docker compose -f compose.yml -f compose.prod.yml up -d
# voir le résultat de la fusion, sans rien lancer
docker compose -f compose.yml -f compose.prod.yml config
----

[%step]
* Profils : activer ou non des *services* (un Kibana, un outil de debug, un runner).
* Override : changer la *configuration* d'un même service selon l'environnement (ports, limites, `restart`).
* C'est ce que demande le complément « Multi-environnements » du projet final.

[.notes]
--
Mesuré le 2026-10-13 (Compose 5.5.1) : un `compose.override.yml` à côté de `compose.yml` est fusionné sans option (ses `ports` apparaissent dans `docker compose config`) ; avec `-f compose.yml -f compose.prod.yml`, l'override n'est plus lu, seul `compose.prod.yml` s'ajoute.
Les fichiers suivants complètent ou remplacent les clés du premier : listes de ports ajoutées, valeurs simples remplacées. `docker compose config` est le seul moyen sûr de voir le résultat.

== ➡️🔄 Les ancres dans `docker compose` ⚓

Docker Compose permet de définir et de gérer plusieurs services Docker dans un seul fichier YAML.
[%step]
- Les ancres (`&`) et les alias (`*`) sont des fonctionnalités YAML qui peuvent être utilisées dans Docker Compose pour réutiliser des configurations.
- Une ancre donne un nom à un objet ou à une valeur dans un fichier YAML.
Elle est définie en utilisant l'opérateur `&` suivi d'un nom unique.

[%step]
[source,yaml]
----
x-slides-base: &slides-base
  build:
    context: ./
----
[%step]
Dans cet exemple, `&slides-base` est l'ancre, posée sur un objet avec une clé `build`.
`x-slides-base` est un champ d'extension : Compose ignore toute clé de premier niveau qui commence par `x-`.

[.notes]
--
Deux mécanismes à séparer au tableau :
1. `x-slides-base` : clé `x-`, que Compose ignore au lieu de refuser une clé inconnue. C'est le « parking » de l'ancre.
2. `&slides-base` / `*slides-base` / `<<:` : du YAML pur, pas du Compose. `<<:` fusionne le contenu de l'ancre dans le service ; les clés écrites à côté l'emportent.
Montrer le résultat réel : `docker compose config` affiche le fichier après fusion, sans ancre.
Utile pour le projet : factoriser `logging`, `restart` et `deploy` communs à tous les services.
--

[%auto-animate]
== ➡️🔄 Les ancres dans `docker compose` ⚓

Les ancres peuvent être référencées ailleurs dans le fichier YAML en utilisant l'opérateur `*`.
[%step]
[source,yaml]
----
services:
  serve:
    <<: *slides-base
----
[.small%step]
- Les ancres permettent de réutiliser des configurations, ce qui rend le fichier Docker Compose plus lisible et plus facile à maintenir.
- Si vous devez modifier une configuration qui est utilisée à plusieurs endroits, vous pouvez simplement modifier l'ancre.
- ⚠️ `<<:` fusionne en surface : redéfinir `environment:` dans le service *remplace* toute la liste de l'ancre, au lieu de la compléter.
- En conclusion, les ancres et les alias sont des outils puissants pour gérer des configurations complexes dans Docker Compose. Ils permettent de réduire la duplication et d'améliorer la lisibilité de votre fichier Docker Compose.

== Pourquoi une image construite, et pas l'image publiée ? 📄

L'image publiée `ghcr.io/astefanutti/decktape` ne suffit plus telle quelle.
[%step]
* Le PDF passe par deux étapes : decktape rend les diapositives en 2048x1536, puis `ghostscript` réduit le fichier. L'image publiée n'a pas `ghostscript`.
* Chromium ne démarre dans le conteneur qu'avec `--no-sandbox` et `--disable-gpu`. Ces options vivent dans `entrypoint.sh`, d'où l'absence de `command:` dans le service.
* L'image ne déclare un `HOME` que pour l'uid 1000. Avec un autre uid, Chromium échoue sur `chrome_crashpad_handler: --database is required` : d'où `HOME=/tmp`.
[%step]
Un petit `Dockerfile` `FROM ghcr.io/astefanutti/decktape` règle les deux premiers points ; Compose le construit avec `build:`.

[.notes]
--
Message à retenir, pas les détails : une image publiée sert de base, on la complète avec un petit Dockerfile `FROM ...` plutôt que de bricoler dans `command:`.
Le troisième point (HOME seulement pour l'uid 1000) est la conséquence de `user: ${CURRENT_UID}` : en changeant d'utilisateur, on perd ce que l'image avait préparé pour le sien. Même famille de problèmes qu'à l'exercice 2 du chapitre sécurité.
--

include::../code-samples/compose/cours/docker-compose.yml[tags=utilisateur]

[%step]
* Dans un conteneur, chaque processus tourne sous un utilisateur donné.
* Par défaut, cet utilisateur est root, mais pour des raisons de sécurité, il est souvent recommandé d'exécuter les processus en tant qu'utilisateur non root.
* Cette ligne définit l'ID de l'utilisateur qui exécutera les commandes à l'intérieur du conteneur Docker à la valeur de la variable d'environnement `CURRENT_UID`.
* La syntaxe `${CURRENT_UID}` est utilisée pour accéder à la valeur d'une variable d'environnement.
* Dans ce cas, Docker Compose recherchera une variable d'environnement nommée `CURRENT_UID` et utilisera sa valeur.
* Si `CURRENT_UID` n'est pas défini, Docker Compose *n'échoue pas* : même avertissement, même chaîne vide. `user:` reçoit une valeur vide.
* Le conteneur démarre donc *en root* — exactement l'inverse de ce que cette ligne cherchait à obtenir.

[.notes]
--
Distinguer au tableau : `USER` dans le Dockerfile fixe l'utilisateur par défaut de l'image ; `user:` dans Compose le remplace au lancement, sans reconstruire.
Ici, `user:` sert à écrire dans `dist/` (montage bind) avec l'uid de l'étudiant, pour que les fichiers produits lui appartiennent sur l'hôte.
Mesuré le 2026-10-13 : `user: ""` donne bien `uid=0(root)`.
Le chapitre sécurité reprend la question sous l'angle « pas de root » : c'est le même réglage.
--

== 🛡️ Rendre une variable vraiment obligatoire

Permissif :

[source,yaml]
----
user: ${CURRENT_UID}
----

Obligatoire :

[source,yaml]
----
user: ${CURRENT_UID:?CURRENT_UID est obligatoire}
----
[%step]
* `+${VAR}+` est permissif : variable absente, valeur vide, on continue.
* `+${VAR:?message}+` échoue pour de bon, dès `docker compose config` : le message s'affiche et le code de sortie est 1.
* Rien ne démarre, donc rien ne démarre en root.
* C'est la forme à écrire quand la valeur est obligatoire.
* C'est celle qu'utilise le `docker-compose.yml` à la racine de ce dépôt : sans `CURRENT_UID` (que `make` fournit), il s'arrête au lieu de construire en root.

[.notes]
--
Deux formes, une différence : `${VAR:?msg}` échoue si VAR est absente OU vide ; `${VAR?msg}` seulement si elle est absente. Le chapitre sécurité utilise la seconde : pour un mot de passe, préférer la première, sinon une ligne `DB_PASSWORD=` vide dans `.env` passe.
À retenir pour le projet : toutes les variables sans valeur par défaut raisonnable en `:?`.

== 🐋 Tini dans Docker

== 🤔 Pourquoi le PID 1 est-il spécial ?

[source,bash]
----
docker container run --rm alpine ps
# PID   USER     TIME  COMMAND
#     1 root      0:00 ps
----

[%step]
* Dans un conteneur, la commande lancée devient le processus n°1.
* Sur un Linux classique, le PID 1 est `init` : il récolte les processus orphelins terminés (les « zombies »).
* Le noyau protège le PID 1 : un signal qu'il ne gère pas explicitement (le SIGTERM de `docker container stop`) est ignoré.
* Docker attend alors, puis tue le conteneur (SIGKILL, code de sortie 137).

[.notes]
--
Mesuré le 2026-10-13 (Docker 29.8.2) : `alpine sleep 300` sans init met 3,3 s à s'arrêter, code 137 ; avec `--init`, 0,3 s, code 143 (SIGTERM reçu et traité).
`docker container run --rm --init alpine ps` montre `/sbin/docker-init -- ps` en PID 1 : c'est Tini, embarqué dans Docker.
--

== 🤔 Qu'est-ce que Tini ?

Tini est un `init` minuscule mais valide pour les conteneurs. Il est conçu pour être le système init le plus simple possible.

== 🛠️ Que fait Tini ?

Tini fait deux choses :

. Il lance votre processus comme son enfant direct (pas comme petit-enfant, comme le ferait un shell).
. Il relaie ensuite les signaux à cet enfant, et récolte les processus orphelins qui lui reviennent.

== 🎯 Pourquoi Tini est-il utile dans Docker ?

. Docker exécute un seul processus dans un conteneur par défaut. Quand un processus meurt, ses enfants orphelins sont rattachés au PID 1 ; si personne ne les récolte, ils restent à l'état de zombies.
. Tini, en PID 1, récolte ces orphelins et transmet les signaux : `docker container stop` arrête alors proprement l'application.

== 🐋 Tini dans notre Dockerfile

Dans notre Dockerfile, nous utilisons Tini comme point d'entrée :

[source,dockerfile]
----
ENTRYPOINT ["/sbin/tini","-g","gulp"]
----

. Cela signifie que Tini est le premier processus qui est lancé dans notre conteneur.
. Il lancera ensuite `gulp` en tant que processus enfant.
. Avec `-g`, tout signal envoyé au conteneur est relayé par Tini à tout le *groupe* de `gulp` (gulp et ses sous-processus).
. Les processus orphelins qui finissent rattachés au PID 1 sont récoltés par Tini.

[.notes]
--
Tant que gulp vit, ses enfants zombies restent les siens : Tini ne récolte que les orphelins.
Mesuré le 2026-10-13 : `tini -g` en PID 1, `docker stop` → le `trap TERM` de l'enfant s'exécute, arrêt en 0,5 s.
--

== 🐋 Tini sans toucher au Dockerfile

[source,yaml]
----
services:
  app:
    image: mon_image
    init: true
----

[%step]
* `init: true` (ou `docker container run --init`) : Docker injecte son propre Tini, `docker-init`, en PID 1.
* Pas besoin d'`apk add tini` ni de changer l'`ENTRYPOINT`.
* Pour le projet : une ligne, qui règle les arrêts lents (code 137 au lieu de 143).

[.notes]
--
Mesuré le 2026-10-13 : `init: true` → PID 1 = `docker-init`, et `docker-init --version` → `tini version 0.19.0`.
--

Cette configuration de docker compose concerne Docker BuildKit, une fonctionnalité de Docker qui améliore les performances de construction des images Docker.

* La ligne `DOCKER_BUILDKIT ?= 1` vérifie si la variable d'environnement `DOCKER_BUILDKIT` est déjà définie.
** Si ce n'est pas le cas, elle lui attribue la valeur `1`, ce qui active Docker BuildKit.
* De même, `COMPOSE_DOCKER_CLI_BUILD ?= 1` vérifie si la variable d'environnement `COMPOSE_DOCKER_CLI_BUILD` est déjà définie.
** Si ce n'est pas le cas, elle lui attribue la valeur `1`.
** Elle servait à l'ancien `docker-compose` (v1, en Python), qui ne passait pas par BuildKit sans elle.
[%step]
Aujourd'hui, ces deux lignes sont historiques : BuildKit est le constructeur par défaut, et Compose v2 ignore `COMPOSE_DOCKER_CLI_BUILD`. Elles ne changent plus rien ; dans un nouveau projet, ne pas les recopier.

Source : https://docs.docker.com/compose/how-tos/environment-variables/envvars/ (section « Unsupported in Compose V2 »).
