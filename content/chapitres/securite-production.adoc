== Projet Fil Rouge : SecureVote

SecureVote : Une application de vote en ligne moderne

[%step]
* Frontend React (interface de vote)
* Backend API Python Flask
* Base de données PostgreSQL
* Redis pour le cache
* Nginx comme reverse proxy

**Dépôt GitHub :** https://github.com/gounthar/securevote

[.notes]
--
Cette application représente un cas d'usage réaliste : une stack web complète typique des applications modernes.
L'aspect "vote" rend le projet concret et engageant.
Les étudiants vont manipuler 5 technologies différentes, ce qui reflète la réalité du DevOps.
Insister sur le fait que c'est LEUR projet pour les 3 heures : ils vont le faire évoluer eux-mêmes.

**STACK TECHNIQUE EXPLIQUÉE :**

• **Flask (Python)** : Framework web léger pour API REST. Alternative à Django (plus lourd), Express.js (Node), ou Spring (Java).
  - Très utilisé pour des APIs rapides et microservices
  - Langage : Python (facile à lire même sans le connaître)
  - Port : 5000 par défaut
  - Rôle ici : Gère les requêtes HTTP (GET /votes, POST /vote), connexion DB, logique métier

• **React (JavaScript)** : Bibliothèque JavaScript pour interfaces utilisateur (pas un framework complet comme Angular ou Vue).
  - Développé par Facebook, très populaire (Netflix, Airbnb, etc.)
  - Langage : JavaScript/JSX
  - Port : 3000 en développement (webpack dev server)
  - Rôle ici : Affiche l'interface de vote, boutons, résultats en temps réel

• **PostgreSQL** : Base de données relationnelle robuste (alternative open-source à Oracle, MySQL).
  - Stockage persistant des données
  - Port : 5432 par défaut
  - Rôle ici : Stocke les votes, les options de vote, les résultats

• **Redis** : Base de données en mémoire ultra-rapide, utilisée comme cache.
  - Prononcé "RED-iss" (Remote Dictionary Server)
  - Port : 6379 par défaut
  - Rôle ici : Cache les résultats de vote pour éviter de requêter PostgreSQL à chaque fois (performance !)

• **Nginx** : Serveur web et reverse proxy très performant (concurrent d'Apache).
  - Prononcé "engine-x"
  - Port : 80 (HTTP) / 443 (HTTPS)
  - Rôle ici : Point d'entrée unique, route les requêtes vers frontend (/) ou backend (/api)

**POURQUOI CETTE STACK ?** C'est une architecture moderne typique : frontend SPA (Single Page App) + API REST + DB + cache + reverse proxy.
On la retrouve chez des entreprises comme Uber, Spotify, Instagram (avec des variations).

== Architecture de l'application

[source,yaml]
----
services:
  frontend:    # React app
  backend:     # Flask API
  database:    # PostgreSQL
  cache:       # Redis
  proxy:       # Nginx
----

Architecture multi-tiers classique pour DevOps

[.notes]
--
Architecture en 5 services : c'est suffisamment complexe pour être intéressant, mais pas trop pour 3h.
Proxy en point d'entrée unique : seul port exposé en prod, pattern essentiel à comprendre.
Cache Redis : montre l'importance de la performance en production.
Cette architecture se retrouve dans 80% des applications web modernes.

**COMMENT LES COMPOSANTS COMMUNIQUENT :**

1. **Utilisateur → Nginx (port 8080)** : L'utilisateur accède à http://localhost:8080
   - Nginx reçoit TOUTES les requêtes (le "portier" de l'application)

2. **Nginx → Frontend (port 3000)** : Pour les pages web (/, /index.html, /static/...)
   - Nginx fait du "proxy_pass" : il redirige la requête vers React
   - React retourne du HTML/CSS/JavaScript

3. **Nginx → Backend (port 5000)** : Pour les requêtes API (/api/...)
   - Exemple : POST /api/vote → Nginx redirige vers Flask
   - Flask traite la logique et retourne du JSON

4. **Backend → Database (port 5432)** : Flask se connecte à PostgreSQL
   - Utilise le driver psycopg2 (bibliothèque Python pour PostgreSQL)
   - Exemples : INSERT INTO votes, SELECT COUNT(*) FROM votes

5. **Backend → Cache (port 6379)** : Flask interroge Redis en premier
   - Si donnée en cache → retour immédiat (rapide !)
   - Si pas en cache → requête PostgreSQL + mise en cache pour la prochaine fois

**AVANTAGES DE CETTE ARCHITECTURE :**
- **Séparation des responsabilités** : chaque service a un rôle clair
- **Scalabilité** : on peut dupliquer frontend/backend indépendamment
- **Sécurité** : seul Nginx est exposé, les autres services sont internes
- **Performance** : Redis évite de surcharger PostgreSQL

**EN PHASE 1** : Tous les ports sont exposés (5432, 6379, 5000, 3000, 8080) = VULNÉRABILITÉ !
**EN PHASE 2/3** : Seul le port 8080 (Nginx) est exposé, le reste est interne.

== Sécurité Docker : Les fondamentaux

Les 3 piliers de la sécurité Docker :

[%step]
. **Images sûres** : Bases fiables, sans vulnérabilités
. **Runtime sécurisé** : Isolation, utilisateurs non-root
. **Secrets protégés** : Pas de mots de passe en clair

[.notes]
--
Framework simple pour mémoriser : 3 piliers = 3 zones d'intervention.
Images = la BASE, si elle est pourrie, tout le reste est compromis.
Runtime = pendant l'exécution, principe du moindre privilège.
Secrets = la donnée la plus sensible, jamais en clair.
Cette structure va guider toute la Phase 2.
--

== Principe du moindre privilège

[quote]
____
Un conteneur ne devrait avoir QUE les permissions nécessaires à son fonctionnement
____

[%step]
* Pas d'exécution en tant que root
* Capacités Linux minimales
* Système de fichiers en lecture seule quand possible
* Réseau isolé

== Installation de Trivy

**Méthode rapide (pour le TP) :**

[source,bash]
----
# Installation directe du binaire
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh \
  | sudo sh -s -- -b /usr/local/bin v0.75.0
trivy --version
----

WARNING: `curl | sudo sh` est pratique MAIS dangereux en production !

**Méthode sécurisée (recommandée) :**

[source,bash]
----
# 1. Télécharger le script
curl -sfL https://raw.githubusercontent.com/aquasecurity/trivy/main/contrib/install.sh -o /tmp/trivy-install.sh

# 2. Inspecter le contenu
less /tmp/trivy-install.sh

# 3. Exécuter après vérification
sudo sh /tmp/trivy-install.sh -b /usr/local/bin v0.75.0
----

WARNING: Toujours une version explicite (incident de mars 2026, voir les notes).

[.notes]
--
**IMPORTANT - PRATIQUE vs SÉCURITÉ :**

Dans un chapitre sécurité, il est crucial de montrer LES DEUX approches :

**Méthode rapide (curl | sudo sh) :**
- ✅ Pratique pour le TP (gain de temps)
- ✅ Recommandée par la doc officielle Trivy (avec un tag de version, comme ici)
- ❌ DANGEREUX : exécute du code non vérifié en root
- ❌ Attaque potentielle : script modifié = compromission totale

**Méthode sécurisée (télécharger → inspecter → exécuter) :**
- ✅ Permet de vérifier le contenu avant exécution
- ✅ Bonne pratique sécurité (principe de précaution)
- ❌ Plus long (3 étapes au lieu d'1)

**POUR LE TP :**
- Démonstration : montrer les DEUX approches
- Insister : "Je fais rapide pour le TP, MAIS en production..."
- Exercice pédagogique : comparer les deux = enseignement du compromis pratique/sécurité

**MESSAGE CLÉ :**
"En sécurité, il y a souvent un compromis entre praticité et sécurité.
Pour un TP pédagogique, curl|sh est OK. En production sur serveur critique, TOUJOURS inspecter avant."

Fonctionne sur toutes les distributions : Debian (y compris Trixie), Ubuntu, RHEL, etc.
Le dépôt apt officiel marche aussi, y compris sur trixie : il utilise maintenant une suite `generic`.

**L'INCIDENT DE MARS 2026 (GHSA-69fq-xp46-6x23) :**
- Le 2026-03-19, la chaîne de publication de Trivy a été compromise : la v0.69.4 malveillante était « latest » pendant ~3 h, sur GitHub Releases, les paquets deb/rpm, get.trivy.dev et les images. Docker Hub a reçu aussi 0.69.5 et 0.69.6 malveillantes le 2026-03-22.
- Sans tag, `install.sh` et `aquasec/trivy` sans version installaient la version piégée.
- Le script vérifie le sha256 contre le `checksums.txt` de la MÊME release : ça ne protège pas d'une release compromise à la source.
- Éviter 0.69.4 à 0.69.6. Vérification plus forte : signature Sigstore (`cosign verify-blob` avec les fichiers `.sigstore.json` publiés depuis la v0.68.1).
- Message à faire passer : l'outil de sécurité est lui-même une dépendance de la chaîne d'approvisionnement.

**PRODUCTION - VERSION PINNING ET INTÉGRITÉ :**

Pour une sécurité maximale en production, deux améliorations essentielles :

1. **Version pinning** : Pin une version spécifique au lieu de "latest"
   - Évite les breaking changes inattendus
   - Le script d'installation supporte la sélection de release
   - Exemple : `curl -sfL ... | sudo sh -s -- -b /usr/local/bin v0.75.0`

2. **Vérification d'intégrité** : Checksum ou signature avant exécution
   - Télécharger le checksum depuis GitHub releases
   - Vérifier avec `sha256sum --check`
   - Garantit que le binaire n'a pas été altéré EN ROUTE, pas que la release elle-même est saine (voir l'incident de mars 2026) : pour ça, la signature Sigstore

Ces étapes sont omises dans le TP pour simplicité, mais OBLIGATOIRES en production CI/CD.

== Installation Trivy : Alternatives

**Si vous n'avez pas les droits sudo :**

[source,bash]
----
# Via Docker (aucune installation nécessaire)
docker container run --rm \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v $HOME/.cache/trivy:/root/.cache/trivy \
  aquasec/trivy:0.75.0 image python:3.11
----

TIP: Pin la version (`:0.75.0`, jamais `latest`) et persist le cache (`-v $HOME/.cache/trivy`) pour performances

**Autres systèmes :**

[%step]
* **macOS :** `brew install trivy`
* **Debian/Ubuntu (y compris trixie) :** dépôt apt officiel, suite `generic` (voir documentation)

[.notes]
--
**MÉTHODE DOCKER :**
- Aucune installation nécessaire
- Garantit que tout le monde a la même version
- Peut être plus lent la première fois (télécharge l'image)
- Syntaxe un peu plus longue

**CHOIX POUR LE TP :**
- Démonstration enseignant : script d'installation (rapide, propre)
- Étudiants : script d'installation OU Docker selon permissions
- Première utilisation : le scan sera lent (~30s) car télécharge la base CVE (~130 Mo, ~1,5 Go une fois décompressée)
- Méthode Docker : le cache appartient à root sur l'hôte (le conteneur tourne en root) ; `sudo rm` pour le supprimer
- Mise à jour de la base : `trivy image --download-db-only`

**TROUBLESHOOTING :**
- Permission denied → Ajouter sudo ou utiliser méthode Docker
- Erreur "trixie Release not found" (vieille doc apt) → utiliser la suite `generic` ou le script

== Utilisateurs non-root

**Problème :** Par défaut, les processus s'exécutent en tant que root

[source,dockerfile]
----
FROM python:3.11
COPY app.py /app/
CMD ["python", "/app/app.py"]  # Root !
----

WARNING: Si compromis, l'attaquant a les privilèges root !

[.notes]
--
Erreur N°1 des débutants Docker : tout tourne en root par défaut.
Analogie : c'est comme lancer toutes vos apps Windows en "Administrateur" en permanence.
Si un attaquant exploite une faille dans votre app Python, il a root sur le conteneur.
Avec root, il peut : installer des outils, scanner le réseau, pivoter vers d'autres conteneurs.
Montrer docker container exec <container> id → retourne "uid=0(root)" = MAUVAIS !
--

== Solution : Utilisateur dédié

[source,dockerfile]
----
FROM python:3.11-slim

RUN groupadd -r appuser && useradd -r -g appuser appuser
WORKDIR /app
COPY app.py /app/
RUN chown -R appuser:appuser /app

USER appuser
CMD ["python", "/app/app.py"]
----

== Bonnes pratiques utilisateur

[%step]
* Toujours créer un utilisateur dédié
* UID qui ne coïncide avec aucun compte de l'hôte propriétaire de fichiers montés
* Ne jamais revenir à root après USER
* Vérifier : `docker container exec <container> id`

[.notes]
--
Pourquoi `id` et pas `whoami` ? `whoami` traduit l'UID en nom via `/etc/passwd`.
Avec `docker container run --user 1001:1001`, l'UID 1001 n'existe pas dans l'image :
`whoami: cannot find name for user ID 1001` (image Debian comme python:3.11-slim).
`id` affiche l'UID dans tous les cas : `uid=1001 gid=1001 groups=1001`.
Point à faire passer : le noyau ne connaît que des numéros, le nom n'est qu'une étiquette dans `/etc/passwd`.
--

== Comprendre les UID Linux

Linux numérote les utilisateurs (User ID) :

[%step]
* **UID 0** : root (super-utilisateur)
* **UID 1-999** : comptes système (www-data, postgres, redis...)
* **UID ≥ 1000** : utilisateurs normaux et applications

[%step]
WARNING: Le noyau ne voit que des numéros : avec des volumes montés, un UID de conteneur qui coïncide avec un compte de l'hôte (33 = www-data, mais aussi 1000 = souvent le premier utilisateur humain) accède à ses fichiers.

[.notes]
--
**POURQUOI C'EST IMPORTANT :**

Si vous créez un utilisateur avec UID 33 (www-data) dans votre conteneur,
et que l'hôte a AUSSI www-data (UID 33), le conteneur pourra accéder aux fichiers
de www-data sur l'HÔTE via les volumes montés = faille de sécurité !

**BONNE PRATIQUE :**
- Ce n'est pas la plage (< ou ≥ 1000) qui compte, c'est la collision avec un compte de l'hôte qui possède des fichiers montés.
- `useradd appuser` sans option donne 1000 : l'UID du premier compte humain de beaucoup de machines (c'est le cas sur un poste WSL). Pas plus sûr que 33.
- Sans volumes montés : `useradd -r` acceptable (crée un UID système, 999 dans la phase 2).
- Avec volumes montés : choisir un UID explicite, absent de l'hôte (`useradd -u 10001`).

Dans SecureVote, `-r` est acceptable car pas de volumes montés critiques avec l'hôte.
--

== UID : Exemple pratique

[source,dockerfile]
----
# RISQUÉ : UID d'un compte connu de l'hôte
RUN useradd -u 33 appuser
# Conflit possible si l'hôte a www-data (UID 33) !

# RISQUÉ AUSSI : sans option, useradd donne 1000,
# souvent le premier utilisateur humain de l'hôte
RUN useradd appuser

# MIEUX : un UID explicite, absent de l'hôte
RUN useradd -u 10001 appuser
----

[%step]
Vérifier : `docker container exec <container> id`

[.notes]
--
Montrer la commande `id` dans un conteneur pour voir l'UID assigné.
Exemple de résultat : uid=1001(appuser) gid=1001(appuser) groups=1001(appuser)

Pour les étudiants : expliquer que c'est comme les numéros de téléphone -
il faut éviter que deux personnes aient le même numéro !

L'option `-r` dans `useradd -r` crée un "system user" avec UID < 1000.
C'est historique : les services système (Apache, Nginx, PostgreSQL) utilisent des UID bas.

**PRODUCTION - USER NUMÉRIQUE POUR PORTABILITÉ :**

Pour maximiser la portabilité entre différentes images de base :
- Préférer `USER 1001:1001` au lieu de `USER appuser`
- Évite les lookups de noms d'utilisateurs qui peuvent échouer
- Garantit cohérence même si `/etc/passwd` diffère entre images
- Crucial avec volumes montés partagés entre plusieurs conteneurs

Exemple robuste :
```dockerfile
RUN groupadd -g 1001 appgroup && useradd -u 1001 -g 1001 appuser
USER 1001:1001
```

Cette approche numérique est LA meilleure pratique pour production/Kubernetes.
--

== Gestion des secrets

**Mauvaise pratique :**

[source,yaml]
----
environment:
  - POSTGRES_PASSWORD=super_secret_123  # NON !
----

WARNING: Visible dans `docker container inspect`, logs, historique !

[.notes]
--
Piège classique : secrets en clair dans docker-compose.yml = COMMITÉS sur Git = PUBLICS.
Anecdote : chercher "removed password" sur GitHub = des millions de résultats.
Les secrets restent dans l'historique Git même après suppression !
docker container inspect montre TOUTES les variables d'env = un attaquant peut lire.
Les logs peuvent accidentellement afficher les secrets lors du démarrage.
Message clé : les secrets ne doivent JAMAIS être versionnés.
--

== Bonne pratique : Fichiers .env

**Étape 1 : Créer le fichier .env**

[source,bash]
----
# .env (à ne JAMAIS commiter)
DB_PASSWORD=super_secret_123
----

**Étape 2 : Protéger avec .gitignore**

[source,bash]
----
# .gitignore
.env
secrets/
----

**Étape 3 : Utiliser dans docker-compose.yml**

[source,yaml]
----
environment:
  POSTGRES_PASSWORD: ${DB_PASSWORD}
  API_KEY: ${API_KEY:-default_key}     # Valeur par défaut si absent
  DB_HOST: ${DB_HOST?required}          # Erreur si non défini
----

TIP: Docker Compose charge automatiquement le fichier .env

**Syntaxes avancées :**

[%step]
* `${VAR:-default}` : Utilise `default` si VAR n'est pas définie
* `${VAR?error message}` : Échoue avec message si VAR manquante
* Utile pour séparer config obligatoire vs optionnelle

[.notes]
--
`${VAR:?message}` échoue aussi si la variable est VIDE : préférable pour un mot de passe (une ligne `DB_PASSWORD=` passe sinon).
`.env` règle le problème de Git, pas celui de `docker container inspect` : la valeur y reste visible (mesuré sur la phase 2 : `SECRET_KEY`, `DATABASE_URL` avec le mot de passe). Transition vers les secrets Compose, diapo suivante.
--

== Alternative 1 : Docker Secrets

**Avec Compose, sans Swarm :**

[source,yaml]
----
services:
  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./secrets/db_password.txt   # secrets/ est dans .gitignore
----

[%step]
* Le fichier est monté dans `/run/secrets/db_password`, et la valeur n'apparaît pas dans `docker container inspect`.
* Avec Swarm en plus : secrets chiffrés dans le cluster, montés en RAM (tmpfs).

[.notes]
--
Mesuré le 2026-10-13 (Compose 5.5.1, sans Swarm) : postgres démarre avec `POSTGRES_PASSWORD_FILE`, `cat /run/secrets/db_password` affiche la valeur, `docker inspect` ne la contient pas.
L'image postgres ne lit pas `/run/secrets` d'elle-même : c'est la variable `*_FILE` qui le lui dit. Beaucoup d'images officielles suivent cette convention.
Hors Swarm, c'est un simple montage du fichier de l'hôte, sans chiffrement : le chiffrement au repos et le tmpfs sont propres à Swarm.
Version Swarm : `docker swarm init`, `echo "secret123" | docker secret create db_password -`, puis `docker service create --secret db_password -e POSTGRES_PASSWORD_FILE=/run/secrets/db_password postgres:15-alpine`.
--

[.notes]
--
**DOCKER SECRETS - GUIDE DÉTAILLÉ**

Qu'est-ce que c'est ?
- Système de gestion de secrets intégré à Docker Swarm (orchestrateur Docker natif)
- Secrets stockés cryptés dans le cluster Swarm
- Montés comme fichiers dans /run/secrets/ (en RAM, jamais sur disque)
- Les secrets ne transitent JAMAIS sur le disque dur, toujours en mémoire

**Avantages :**
✅ Natif Docker, pas de service externe à installer
✅ Crypté au repos et en transit (TLS mutuel entre nœuds)
✅ Accès contrôlé par service (seuls les services autorisés peuvent lire)
✅ Rotation possible (créer nouveau secret, redéployer service)
✅ Gratuit, inclus dans Docker

**Inconvénients :**
❌ Chiffrement et stockage en RAM : Swarm seulement. Compose seul monte un simple fichier (déjà mieux que l'environnement)
❌ Moins de fonctionnalités que Vault (pas de rotation automatique, audit limité)
❌ Courbe d'apprentissage Swarm si vous utilisez Compose

**Comment ça fonctionne :**
1. Créer le secret : `docker secret create db_password secret.txt`
2. Attribuer au service : `docker service create --secret db_password myapp` (et lui dire où lire : `-e POSTGRES_PASSWORD_FILE=/run/secrets/db_password` pour postgres)
3. Application lit `/run/secrets/db_password` (fichier en RAM)

**Quand l'utiliser :**
- Environnements Docker Swarm en production
- Petites/moyennes infrastructures (5-50 conteneurs)
- Alternative simple à Vault pour débuter
- Besoin de secrets cryptés sans infrastructure externe

**Pour SecureVote :**
Non utilisé dans le TP (on reste sur Compose), mais évolution possible si migration vers Swarm.

== Alternative 2 : HashiCorp Vault

**Solution d'entreprise pour secrets**

[%step]
* Serveur centralisé avec API REST
* Rotation automatique des credentials
* Audit complet et secrets dynamiques

[source,bash]
----

[%step]
WARNING: Nécessite infrastructure dédiée (serveur Vault)

[.notes]
--
**VAULT - SOLUTION ENTERPRISE**

Qu'est-ce que c'est ?
- Solution d'entreprise dédiée à la gestion de secrets (HashiCorp)
- Serveur centralisé de secrets avec API REST
- Audit complet, rotation automatique, durée de vie des secrets
- "Fort Knox" des secrets : le standard de l'industrie

**Avantages :**
✅ Solution la plus complète du marché
✅ Rotation automatique des secrets (DB credentials, API keys, certificats)
✅ Audit trail complet (qui a accédé à quoi, quand, depuis où)
✅ Secrets dynamiques (génère des credentials temporaires à la demande)
✅ Intégration avec cloud providers (AWS, Azure, GCP)
✅ Fonctionne avec Docker Compose, Swarm, Kubernetes, VMs

== Alternative 3 : Cloud Providers

**Services managés AWS / Azure / GCP**

[%step]
* **AWS Secrets Manager** : intégration RDS/Aurora
* **Azure Key Vault** : intégration Azure AD, HSM
* **GCP Secret Manager** : intégration Cloud Run/GKE

[%step]
✅ Entièrement managé, haute disponibilité
❌ Vendor lock-in, coût à l'usage

[.notes]
--
**CLOUD PROVIDERS - SERVICES MANAGÉS**

Qu'est-ce que c'est ?
- Services managés de gestion de secrets par les cloud providers
- Intégration native avec les autres services du cloud
- Zéro maintenance, facturation à l'usage

**Les 3 grands providers :**

**1. AWS Secrets Manager**
- Rotation automatique pour RDS, Aurora, Redshift, DocumentDB
- Intégration native avec Lambda, ECS, EC2 via IAM roles
- Versioning automatique des secrets
- Coût : ~0.40$/secret/mois + 0.05$/10k requêtes

**2. Azure Key Vault**
- Intégration avec Azure AD pour l'authentification
- HSM hardware optionnel (clés stockées dans modules cryptographiques certifiés)
- Managed identities pour AKS, App Service, Functions
- Coût : pas de coût par secret (offre Standard), ~0.03$/10k opérations

**3. GCP Secret Manager**
- Intégration native avec Cloud Run, GKE, Cloud Functions
- Réplication multi-région automatique
- Audit via Cloud Logging
- Coût : ~0.06$/secret/mois + 0.03$/10k accès

**Avantages :**
✅ Entièrement managé (pas de serveur à maintenir, pas de patching)
✅ Intégration native avec services cloud (IAM, load balancers, etc.)
✅ Rotation automatique pour certains services (RDS sur AWS, etc.)
✅ Haute disponibilité garantie par le provider (SLA 99.9%+)
✅ Audit via CloudTrail / Azure Monitor / Cloud Logging
✅ Facile à démarrer (quelques clics dans la console)

**Inconvénients :**
❌ Vendor lock-in (difficile de migrer vers autre cloud)
❌ Coût à l'usage (peut devenir cher avec 1000+ secrets)
❌ Moins flexible que Vault pour du multi-cloud
❌ Features variables selon provider (AWS plus complet que GCP)

**Comparaison des coûts (exemple 100 secrets, 1M requêtes/mois) :**
- AWS : ~40$ + 5$ = 45$/mois
- Azure : ~3$/mois (opérations seulement)
- GCP : ~6$ + 3$ = 9$/mois
- Vault self-hosted : ~200$/mois (serveur) + temps équipe

**Quand l'utiliser :**
- Infrastructure déjà sur un cloud public (AWS, Azure, GCP)
- Pas d'équipe dédiée pour gérer un Vault
- Budget pour services managés
- Besoin d'intégration native avec services cloud
- Startup/PME qui veut se concentrer sur le produit, pas l'infra

**Pour SecureVote :**
Si déploiement sur AWS/Azure/GCP → excellent choix. Plus simple que Vault, pas de maintenance.

== Alternative 4 : Variables shell

**Passage direct via environnement**

[%step]
* Simple pour dev et CI/CD
* Secrets injectés au runtime

[source,bash]
----
# En une ligne
DB_PASSWORD="secret123" docker compose up -d

# Ou via export
export DB_PASSWORD="secret123"
docker compose up -d
----

[%step]
WARNING: Visible dans l'historique du shell et dans `docker container inspect` !

[.notes]
--
**VARIABLES D'ENVIRONNEMENT SHELL**

Qu'est-ce que c'est ?
- Passer les secrets via variables d'environnement du shell au lancement
- Les secrets restent en mémoire du processus shell
- Méthode la plus simple, mais limitations importantes

**Avantages :**
✅ Très simple, pas de fichier .env à gérer
✅ Secrets restent dans la session shell (pas versionnés)
✅ Utile pour CI/CD (GitLab CI, GitHub Actions injectent des variables)
✅ Pas de dépendance externe
✅ Idéal pour scripts one-shot

**Inconvénients :**
❌ Visible dans `docker container inspect`, et dans `/proc/<pid>/environ` pour root et le même utilisateur (pas dans `ps aux` : seuls les arguments de commande s'y voient)
❌ Reste dans l'historique shell (~/.bash_history) si export
❌ Moins pratique pour plusieurs secrets (commande très longue)
❌ Perd les secrets si session shell se ferme (pas persistant)
❌ Difficile à gérer en équipe (chacun doit set ses variables)

**Exemples d'utilisation :**

[source,bash]
----
# Méthode 1 : Inline (préférable)
DB_PASSWORD="secret123" REDIS_PASSWORD="abc456" docker compose up -d

# Méthode 2 : Export (reste en mémoire shell)
export DB_PASSWORD="secret123"
export REDIS_PASSWORD="abc456"
docker compose up -d

# Méthode 3 : Depuis fichier non versionné
source ~/secrets.sh  # contient les exports
docker compose up -d

# Méthode 4 : CI/CD (GitLab CI exemple)
# Les variables sont injectées par le runner
script:
  - docker compose up -d  # $DB_PASSWORD déjà disponible
----

**Ce qui se voit dans `ps aux`, et ce qui ne se voit pas :**

[source,bash]
----
# Variable d'environnement : PAS dans ps aux
DB_PASSWORD=secret123 docker compose up -d
# Argument de commande : visible par tous les utilisateurs dans ps aux
mysql --password=secret123
----

**Quand l'utiliser :**
- Développement local rapide (test ponctuel)
- CI/CD pipelines (GitLab CI, GitHub Actions, Jenkins)
  - Les secrets sont injectés par le système CI/CD
  - Ne restent pas dans l'historique du runner
- Scripts d'automatisation ponctuels
- Environnements éphémères (conteneurs CI qui sont détruits après)

**Quand NE PAS l'utiliser :**
- Production (trop risqué, pas d'audit)
- Serveurs partagés (historique shell, `docker inspect` pour qui a accès au moteur)
- Secrets critiques (passwords DB prod, API keys sensibles)

**Pour SecureVote :**
Acceptable pour tests locaux rapides. Mais préférer .env pour le TP (plus pédagogique, plus réaliste).
CI/CD bonus : montrer comment GitLab CI/GitHub Actions injectent les secrets.
--

== Le point commun des cinq solutions

À la fin, le secret est **dans** le conteneur :

[%step]
* en variable d'environnement (`.env`, variables shell)
* en fichier sous `/run/secrets/` (Docker Secrets)
* ou en mémoire, lu par l'application via une API (Vault, cloud)
* dans tous les cas, le programme a la valeur en clair

[.step]
**Et si le programme ne recevait jamais le secret ?**

[.notes]
--
Transition : les cinq solutions du tableau règlent le problème du STOCKAGE (ne pas commiter, chiffrer au repos, contrôler l'accès).
Aucune ne règle celui de l'USAGE : le programme finit par détenir la valeur en clair (variable, fichier, ou réponse de l'API Vault/cloud), et un programme compromis (dépendance piégée, agent d'IA qui se trompe, injection de prompt) peut la lire et l'envoyer ailleurs.
Rappel de la diapositive « Mauvaise pratique » : docker container inspect montre toutes les variables d'environnement.
Faire deviner avant la diapositive suivante : où mettre le secret pour que le programme puisse s'en servir sans jamais le voir ?

== Docker Sandboxes : le proxy d'identifiants

image::sbx-proxy-identifiants.svg[Proxy d'identifiants hors de la microVM]

[.small]
_État au 2026-09-24, `sbx` v0.45.1. Outil récent : les commandes peuvent changer._

[.notes]
--
Docker Sandboxes (commande sbx) lance chaque sandbox dans une microVM : noyau propre, démon Docker propre.
Mesuré le 2026-09-24 : noyau 7.0.12 dans la sandbox, 6.8 sur l'hôte. C'est bien une VM, pas un conteneur.

Le point à faire voir sur le schéma : le proxy est HORS de la VM, dans le démon sbx de l'hôte.
- Le secret réel est stocké côté hôte (sbx secret set-custom, ou sbx secret set pour les services connus).
- La VM ne reçoit qu'une valeur de substitution (sbx-cs-... pour un secret personnalisé).
- Toutes les requêtes HTTP(S) de la VM passent par ce proxy (HTTPS_PROXY=http://gateway.docker.internal:3128 dans la sandbox).
- Pour l'hôte déclaré, le proxy remplace la substitution par la valeur réelle dans l'en-tête. Pour tout autre hôte, la substitution part telle quelle.

Idée clé : le proxy ne place jamais le secret dans l'environnement d'exécution (ni variable, ni fichier). C'est un modèle différent des cinq autres, pas une sixième ligne du tableau.
Nuance, deux diapositives plus loin : un hôte déclaré qui renvoie l'en-tête fait quand même entrer la valeur dans la sandbox.

Sources : docs.docker.com/ai/sandboxes/security (« host-side proxy ») et docs.docker.com/ai/sandboxes/configuration/credentials.
--

== Démo : ce que voit la sandbox

Sur l'hôte, un secret factice lié à un seul domaine :

[source,bash]
----
sbx policy init balanced
sbx secret set-custom --host httpbin.org --env DEMO_TOKEN --value valeur-reelle-576
sbx create shell --name demo .
sbx policy allow network httpbin.org
----

Dans la sandbox :

[source,bash]
----
sbx exec demo sh -c 'echo $DEMO_TOKEN'
# sbx-cs-oQlw2y1oLoOzfg5D
sbx exec demo sh -c 'curl -sS -H "Authorization: Bearer $DEMO_TOKEN" https://httpbin.org/headers'
# "Authorization": "Bearer valeur-reelle-576"
----

[.notes]
--
DÉMO SEULEMENT, pas de TP : chaque étudiant aurait besoin d'un compte Docker (sbx login), et d'un poste avec KVM.

Prérequis sur le poste de démo (d'après docs.docker.com/ai/sandboxes/install) :
- Ubuntu 24.04 ou plus récent (le paquet docker-sbx n'existe que dans le dépôt Ubuntu de Docker)
- /dev/kvm accessible, utilisateur dans le groupe kvm
- sbx login fait AVANT le cours (ouvre un navigateur)
- sbx daemon start lancé dans un terminal à part (il reste au premier plan)
À VÉRIFIER sur un poste de l'université avant la séance : rien de tout ça n'y a été testé.

Déroulé mesuré le 2026-09-24 dans un Codespace :
- sbx policy init balanced : sans lui, sbx create refuse de démarrer.
- La valeur de substitution est générée par sbx et change à chaque set-custom : lire la vraie dans la sortie de la commande.
- sbx create shell : environ 1 min 15 au premier lancement (téléchargement de l'image). Lancer AVANT le cours.
- La politique balanced bloque tout domaine non autorisé, d'où sbx policy allow network.
- Guillemets simples autour de sh -c : c'est la sandbox qui développe $DEMO_TOKEN, pas l'hôte.
- --value sur la ligne de commande : acceptable pour une valeur factice, mais elle finit dans l'historique du shell. Ne jamais faire ça avec un vrai secret.

Faire remarquer : echo affiche la substitution, et c'est pourtant la valeur réelle qui arrive chez httpbin.
--

== Ce que le proxy ne protège pas

[%step]
* Le programme peut toujours **utiliser** le secret vers l'hôte déclaré
* Un hôte qui renvoie l'en-tête le révèle : httpbin.org vient de le faire !
* Le proxy déchiffre le HTTPS : il installe sa propre autorité de certification dans la sandbox
* Le secret réel reste sur l'hôte : sans trousseau, dans un fichier

TIP: Le proxy garde la valeur hors de la sandbox, tant que l'hôte déclaré ne la renvoie pas. Il n'empêche jamais de **l'utiliser**.

[.notes]
--
Chaque point a été mesuré le 2026-09-24 :

1. Usage : la sandbox ne connaît pas la valeur, mais toute requête vers httpbin.org part avec. Un agent compromis peut donc agir avec le jeton (créer une issue, pousser du code...) sur le service déclaré. Il ne peut pas lire la valeur, sauf si l'hôte déclaré la renvoie (point 2) : il pourrait alors l'envoyer vers n'importe quel autre domaine autorisé par la politique réseau.
2. Écho : httpbin.org/headers renvoie les en-têtes reçus, donc la réponse contenait "Bearer valeur-reelle-576" DANS la sandbox. Une vraie API (api.github.com) ne renvoie pas l'en-tête Authorization, mais la protection dépend de ce comportement du service distant. Question aux étudiants : quel type d'hôte faut-il éviter de déclarer ?
3. HTTPS : pour réécrire un en-tête chiffré, le proxy fait l'intermédiaire. La sandbox reçoit son certificat d'autorité (variable PROXY_CA_CERT_B64). C'est le même mécanisme qu'un proxy d'entreprise.
4. Stockage : dans le Codespace de test, sbx a affiché « No keychain detected », et le secret est stocké sur disque, protégé par les permissions du fichier. Le secret sort de la VM, pas de la machine.

Détail observé : même sans aucun secret posé, la sandbox reçoit des substitutions pour les services connus, par exemple OPENAI_API_KEY=proxy-managed, et GH_TOKEN=gho_sbxproxymanaged000... qui imite le format d'un vrai jeton GitHub.

Pour un service connu (github, openai, anthropic...), la documentation donne sbx secret set github, la valeur étant demandée de façon interactive. Cette commande-là n'a pas été lancée pour le cours.
--

== Limites de ressources

**Pourquoi limiter ?**

[%step]
* Empêcher monopolisation du serveur
* Garantir stabilité
* Prévoir capacité
* Détecter fuites mémoire

WARNING: Sans limites → 100% CPU/RAM !

[.notes]
--
Histoire réelle : un conteneur mal configuré monopolise 100% CPU d'un serveur = TOUS les autres services ralentissent.
Sans limites, Docker ne protège PAS : un conteneur peut tuer le serveur hôte.
Les limites permettent de PLANIFIER : "j'ai 16 Go, je peux faire tourner 10 conteneurs à 1.5 Go chacun".
Les limites révèlent les fuites mémoire : si votre app atteint systématiquement la limite, elle fuit.
En prod, TOUJOURS définir des limites. C'est comme les ceintures de sécurité : obligatoire.
--

== Définir les limites

[source,yaml]
----
services:
  backend:
    deploy:
      resources:
        limits:
          cpus: '0.5'      # Max un demi-cœur
          memory: 512M     # Max 512 Mo RAM
        reservations:
          cpus: '0.25'     # Ignoré hors Swarm
          memory: 256M     # Limite souple, pas une garantie
----

[.notes]
--
`cpus: '0.5'` = la moitié d'UN cœur, pas 50 % du serveur (`docker inspect` → `NanoCpus=500000000`).
Mesuré le 2026-10-13 (Engine 29.8.2, Compose 5.5.1) : les `limits` sont appliquées par `docker compose` sans Swarm, comme `mem_limit`/`cpus`.
`reservations.cpus` n'est pas appliqué hors Swarm (`CpuShares=0`), et `reservations.memory` devient `MemoryReservation`, une limite souple.
--

== Politiques de redémarrage

[source,yaml]
----
services:
  backend:
    restart: unless-stopped
    # Valeurs possibles (une seule clé restart par service) :
    #   no             : jamais
    #   always         : toujours
    #   on-failure     : si le processus sort en erreur
    #   unless-stopped : sauf arrêt manuel
----

NOTE: Une seule clé `restart:` par service : quatre clés à la suite, c'est un YAML invalide (`mapping key "restart" already defined`).

[%step]
**Production :** Privilégier `unless-stopped` ou `on-failure`

== Restart avec limite

[source,yaml]
----
services:
  backend:
    restart: on-failure:5
----

`on-failure:5` : au plus 5 redémarrages, puis Docker abandonne.

Évite les boucles infinies de redémarrage

[.notes]
--
Pas besoin de Swarm pour limiter les tentatives : `on-failure:N` marche avec `docker compose`.
Mesuré le 2026-10-13 : `on-failure:3` → `RestartCount=3`, puis le conteneur reste arrêté.
`deploy.restart_policy.max_attempts` est aussi appliqué hors Swarm (traduit en `on-failure:N`).
--

== Health checks

[source,yaml]
----
services:
  backend:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s
----

NOTE: Hors Swarm et Kubernetes, un conteneur `unhealthy` n'est *pas* redémarré, même avec `restart: always`. Le healthcheck sert à `depends_on: condition: service_healthy` et à la supervision ; le redémarrage vient de `restart:`, quand le processus meurt.

[.notes]
--
Mesuré le 2026-10-13 : `restart: always` + healthcheck qui échoue toujours → `running`, `unhealthy`, `RestartCount=0`.
Le `curl` du test doit exister dans l'image : le Dockerfile du backend de la phase 3 l'installe exprès.
Health check = le contrôle aérien de vos conteneurs.
Un conteneur peut être "running" mais MORT à l'intérieur (app crashée, connexion DB perdue).
docker container ls montre "Up" mais healthcheck montre "unhealthy" = problème détecté !
Exemple concret : backend démarre en 5s, mais connexion DB prend 30s → start_period: 40s.
interval: 30s = vérifier toutes les 30s, c'est raisonnable (pas trop fréquent, pas trop lent).
retries: 3 = tolérer 3 échecs avant de marquer "unhealthy" = évite les faux positifs.
Le healthcheck doit être RAPIDE (<1s) et LÉGER (pas de requêtes DB lourdes).
--

== 🔧 Troubleshooting Production

[.notes]
--
Section duration: 5 minutes
Practical debugging guide for common production issues

=== Conteneurs qui ne démarrent pas

**Étape 1** : Vérifier les logs

[source,bash]
----
docker container logs nom-conteneur

# OU pour suivre en temps réel
docker container logs -f nom-conteneur
----

**Étape 2** : Inspecter le conteneur

[source,bash]
----
docker container inspect nom-conteneur

# Voir seulement l'état
docker container inspect --format='{{.State.Status}}' nom-conteneur

# Voir le code de sortie
docker container inspect --format='{{.State.ExitCode}}' nom-conteneur
----

**Problèmes courants** :

[cols="2,3,2", options="header"]
|===
| Symptôme
| Cause probable
| Solution

| `host not found in upstream`
| NGINX : résolution DNS statique
| `resolver 127.0.0.11 valid=10s;` (DNS interne de Docker) + `set $backend "app:8080"` + `proxy_pass http://$backend`

| `port is already allocated`
| Port de l'hôte déjà pris
| Changer port ou arrêter service conflictuel

| `cannot assign requested address`
| L'IP de `-p IP:port` n'existe pas sur l'hôte
| Publier sur une IP de la machine, ou sans IP

| `no such file or directory`
| Volume mal configuré
| Vérifier chemin absolu dans volumes

| `permission denied`
| Problème permissions fichier
| Vérifier propriétaire et chmod
|===

=== Health Checks qui échouent

**Étape 1** : Vérifier le status des services

[source,bash]
----
docker compose ps

# Voir seulement les unhealthy
docker compose ps | grep unhealthy
----

**Étape 2** : Inspecter le health check

[source,bash]
----
docker container inspect nom-conteneur | grep -A 20 Health

# Voir uniquement le status
docker container inspect --format='{{.State.Health.Status}}' nom-conteneur

# Voir les derniers logs du health check
docker container inspect --format='{{json .State.Health.Log}}' nom-conteneur | jq
----

**Codes de sortie importants** :

* **0** : Health check réussi ✅
* **1** : Health check échoué (erreur applicative)
* **-1** : Docker n'a pas pu exécuter la sonde (outil absent avec la forme `CMD`, ou délai dépassé : `Health check exceeded timeout`)
* **127** : outil absent avec la forme `CMD-SHELL` (c'est le shell qui ne le trouve pas)

**Problèmes courants** :

[source,text]
----
ExitCode: -1
Output: "exec: \"curl\": executable file not found in $PATH"
→ Solution : Installer curl dans Dockerfile
----

[source,text]
----
ExitCode: 1
Output: "Connection refused"
→ Solution : Vérifier que l'app écoute sur le bon port
----

=== Debugging avec Docker Events

Surveiller tous les événements Docker en temps réel :

[source,bash]
----
# Voir tous les événements
docker events

# Filtrer par conteneur (nom réel : docker compose ps)
docker events --filter container=securevote-backend

# Filtrer par type d'événement
docker events --filter event=start
docker events --filter event=die
docker events --filter event=health_status

# Combiner plusieurs filtres
docker events --filter container=securevote-backend --filter event=health_status
----

**Exemple de sortie** (abrégée) :

[source,text]
----
2026-01-12T10:30:15 container health_status: unhealthy (name=backend)
2026-01-12T10:30:20 container die (name=backend, exitCode=137)
2026-01-12T10:30:25 container start (name=backend)
----

**Utilisation pratique** :

[source,bash]
----
# Dans un terminal, monitorer les événements
docker events --filter event=health_status

# Dans un autre terminal, démarrer les services
docker compose up -d

# Observer en temps réel les changements de santé
----

=== 📊 Checklist de Debugging

Quand un problème survient en production :

[%step]
1. ✅ `docker compose ps` → Identifier les services en erreur
2. ✅ `docker compose logs <service>` → Lire les logs d'erreur
3. ✅ `docker container inspect <conteneur>` → Vérifier la configuration
4. ✅ Si unhealthy : `docker container inspect` pour voir Health.Log
5. ✅ `docker events` en parallèle pour monitoring temps réel

**Commande magique de debugging** :

----
docker compose ps && \
docker compose logs --tail=50 && \

----

Affiche : statuts, logs récents, et écoute les événements !

== Vérifier la signature d'une image

Cosign (projet Sigstore) vérifie qui a signé une image, pas seulement qu'elle est signée :

[source,bash]
----
docker container run --rm ghcr.io/sigstore/cosign/cosign:v3.1.3 verify \
  --certificate-identity=krel-trust@k8s-releng-prod.iam.gserviceaccount.com \
  --certificate-oidc-issuer=https://accounts.google.com \
  registry.k8s.io/pause:3.10
----

[source,text]
----
Verification for registry.k8s.io/pause:3.10 --
The following checks were performed on each of these signatures:
  - The cosign claims were validated
  - Existence of the claims in the transparency log was verified offline
  - The code-signing certificate was verified using trusted certificate authority certificates
----

Avec `--certificate-identity=someone@example.com`, la commande échoue (code de sortie 12) : `no matching signatures`.

[.notes]
--
Sortie réelle, relevée le 2026-09-24 avec Docker 29.8.0 et Cosign v3.1.3. L'image vérifiée
est une image Kubernetes, signée en mode « keyless » par le compte de publication du projet
(`krel-trust@k8s-releng-prod`, celui que la documentation Kubernetes donne pour cette vérification).

Limite de l'exemple : l'outil de vérification vient lui-même d'une image téléchargée. Une
vérification qui établit vraiment la confiance suppose un Cosign obtenu par un canal vérifié
séparément (paquet de la distribution, ou binaire dont la somme de contrôle a été vérifiée).
Faire vérifier une image par elle-même ne prouve rien : une image modifiée peut afficher
« Verified ».

Les tutoriels antérieurs montrent souvent Docker Content Trust (`DOCKER_CONTENT_TRUST=1`,
`docker trust sign`). Ne pas le suivre : la CLI Docker 29 n'a plus de sous-commande
`docker trust`, et le service Notary v1 de Docker Hub (`notary.docker.io`) ferme le
8 décembre 2026. Docker oriente vers Sigstore/Cosign ou Notation.

Signer soi-même : `cosign sign <image>` en mode « keyless » ouvre une authentification OIDC
(GitHub, Google…) et inscrit la signature dans le journal de transparence Rekor.
En CI, l'identité est celle du workflow.
--
