== Contexte

=== Origine de ce Document

Suite à l'analyse des projets d'étudiants de l'examen final 2025-2026 (binômes avec reverse proxy + serveur d'application Java), **trois erreurs critiques** sont apparues de manière récurrente dans les projets les moins bien notés :

1. **Résolution DNS NGINX manquante** : `resolver 127.0.0.11` absent dans nginx.conf
2. **Outils manquants dans les images de base** : `curl` absent pour les health checks
3. **Confusion localhost vs nom de service** : Utilisation de `localhost` au lieu du nom de service Docker

Ces trois erreurs simples ont causé :

* **Échec complet des tests fonctionnels** (0.0/2.0 points)
* **Conteneurs qui ne démarrent jamais** (status: "Created" ou crash loops)
* **Notes finales catastrophiques** : F (Insuffisant) alors que l'architecture était correcte

[IMPORTANT]
====
**Pattern commun identifié** : Les étudiants démontrent une **forte compréhension architecturale** (docker-compose bien structuré, volumes, réseaux personnalisés, ELK stack) mais échouent sur des **détails techniques Docker/NGINX** qui ne sont pas explicitement couverts dans le cours.
====

== 🚨 Piège NGINX : Résolution DNS dans upstream blocks

=== Le Problème

NGINX a un comportement **différent** des autres outils Docker concernant la résolution DNS :

[%step]
* La plupart des outils résolvent les noms de service **dynamiquement** (à chaque requête)
* NGINX résout les hostnames dans `upstream` blocks **une seule fois au démarrage**
* Sans configuration spéciale, NGINX utilise `/etc/resolv.conf` (DNS système)
* Le DNS système Docker **ne connaît pas** les noms de service Docker

=== Exemple de Configuration Défaillante

[source,nginx]
----
events {}

http {
    upstream backend {
        server app-server:8080;  # ❌ ÉCHEC au démarrage !
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
----

**Erreur au démarrage** :
[source,bash]
----
nginx: [emerg] host not found in upstream "app-server:8080" in /etc/nginx/nginx.conf:5
----

**Le conteneur ne démarre jamais !**

=== La Solution : Directive `resolver`

Docker fournit un **serveur DNS interne** à l'adresse **127.0.0.11** qui connaît tous les noms de service.

[source,nginx]
----
events {}

http {
    # ✅ Indique à NGINX d'utiliser le DNS interne Docker
    resolver 127.0.0.11 valid=30s ipv6=off;

    upstream backend {
        server app-server:8080;  # ✅ Fonctionne maintenant !
    }

    server {
        listen 80;
        location / {
            proxy_pass http://backend;
        }
    }
}
----

**Explication des paramètres** :

* `127.0.0.11` : Adresse du DNS interne Docker (fixe pour tous les réseaux)
* `valid=30s` : Cache DNS pendant 30 secondes (évite trop de requêtes DNS)
* `ipv6=off` : Désactive IPv6 (plus rapide, évite les problèmes IPv6 Docker)

=== Quand est-ce nécessaire ?

[cols="2,3,1", options="header"]
|===
| Situation | Directive `resolver` nécessaire ? | Raison

| `upstream` avec noms de service Docker
| ✅ **OUI**
| NGINX doit résoudre via DNS Docker

| `upstream` avec adresses IP
| ❌ Non
| Pas de résolution DNS nécessaire

| `proxy_pass` direct sans upstream
| ⚠️ Parfois
| Requis SEULEMENT si utilisation de variables (ex: `$backend_host`). Pas nécessaire pour noms fixes.

| Services démarrent dans le bon ordre
| ✅ **OUI quand même**
| Plus robuste, fonctionne toujours
|===

[WARNING]
====
**Même si vos services démarrent dans le bon ordre**, ajoutez TOUJOURS `resolver 127.0.0.11` dans vos configurations NGINX avec upstream blocks. C'est une **bonne pratique** qui garantit la robustesse.
====

=== 🎓 Exercice Pratique

Créez un projet avec :

1. Un service `nginx` avec upstream vers `webapp`
2. Un service `webapp` (nginx ou autre)

**Sans `resolver`** :
* Démarrez : les services crashent
* Regardez les logs : `host not found`

**Avec `resolver 127.0.0.11`** :
* Démarrez : tout fonctionne
* Testez : `curl http://localhost/`

=== 📊 En Résumé

[TIP]
====
**Règle d'or NGINX + Docker** :

Si votre nginx.conf contient :
[source,nginx]
----
upstream nom_service {
    server autre_service:port;
}
----

Alors votre nginx.conf DOIT contenir :
[source,nginx]
----
http {
    resolver 127.0.0.11 valid=30s ipv6=off;
    # ...
}
----
====

== ⚠️ Piège : Outils manquants dans les images de base

=== Le Problème

Les health checks utilisent des **commandes shell** exécutées **à l'intérieur du conteneur**.

[IMPORTANT]
====
**Si la commande n'existe pas dans l'image, le health check échoue systématiquement !**
====

=== Exemples d'Images et Outils Disponibles

[cols="2,2,3", options="header"]
|===
| Image de Base | Outils Inclus | Outils ABSENTS

| `debian:12` (full)
| bash, curl, wget, ps, netcat
| (rare)

| `debian:12-slim`
| sh, ps
| ❌ curl, wget, netcat, bash

| `alpine:3.19`
| sh, wget, ps
| ❌ curl, bash, netcat

| `ubuntu:22.04`
| bash, curl, wget
| (rare)

| `nginx:alpine`
| sh, wget
| ❌ curl, bash

| `python:3.11-slim`
| python, ps
| ❌ curl, wget, bash
|===

=== Symptômes d'un Health Check avec Outil Manquant

**docker ps** affiche :
[source,bash]
----
CONTAINER ID   STATUS
abc123         Up 2 minutes (unhealthy)  # ← Health check échoue !
----

**docker inspect** montre :
[source,json]
----
"Health": {
    "Status": "unhealthy",
    "FailingStreak": 15,
    "Log": [
        {
            "ExitCode": 127,
            "Output": "/bin/sh: curl: not found\n"
        }
    ]
}
----

[TIP]
====
**ExitCode 127** = "Command not found" → L'outil n'existe pas dans l'image !
====

=== Solution 1 : Installer l'Outil dans le Dockerfile

**Exemple : Ajouter curl dans une image Debian slim**

[source,dockerfile]
----
FROM debian:12-slim

# Installer curl pour les health checks
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*

# Reste de votre Dockerfile...
COPY app.py /app/
CMD ["python", "/app/app.py"]
----

**Exemple : Ajouter curl dans une image Alpine**

[source,dockerfile]
----
FROM alpine:3.19

# Installer curl pour les health checks
RUN apk add --no-cache curl

# Reste de votre Dockerfile...
COPY app.py /app/
CMD ["python", "/app/app.py"]
----

=== Solution 2 : Utiliser des Alternatives Natives

Si vous ne voulez PAS ajouter de dépendances, utilisez des outils **déjà présents** :

**Alternative à `curl` : Test de fichier**

Au lieu de :
[source,yaml]
----
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8080/health"]  # ❌ curl absent
----

Utilisez :
[source,yaml]
----
healthcheck:
  test: ["CMD-SHELL", "[ -f /app/ready ] || exit 1"]  # ✅ [ ] toujours présent
----

**Alternative à `curl` : wget (présent dans Alpine)**

[source,yaml]
----
healthcheck:
  test: ["CMD", "wget", "--no-verbose", "--tries=1", "--spider", "http://localhost:8080/health"]
----

**Alternative à `curl` : netcat/nc**

[source,yaml]
----
healthcheck:
  test: ["CMD-SHELL", "nc -z localhost 8080 || exit 1"]  # Teste juste la connexion TCP
----

=== Solution 3 : Utiliser Python/Node Built-in

[NOTE]
====
Cette solution s'applique **uniquement** aux images qui contiennent déjà Python ou Node.js (ex: `python:3.11-slim`, `node:18-alpine`, images d'applications Python/Node). N'installez pas Python/Node.js juste pour le health check - utilisez plutôt les Solutions 1 ou 2.
====

Si votre image contient **Python** ou **Node.js**, utilisez-les :

**Health check avec Python** :
[source,yaml]
----
healthcheck:
  test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')"]
----

**Health check avec Node.js** :
[source,yaml]
----
healthcheck:
  test: ["CMD", "node", "-e", "require('http').get('http://localhost:8080/health', (r) => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
----

=== 🎓 Exercice Pratique

1. Créez un Dockerfile basé sur `debian:12-slim`
2. Ajoutez un health check avec `curl`
3. Lancez : observez "unhealthy"
4. Modifiez le Dockerfile pour installer `curl`
5. Relancez : observez "healthy"

=== 📊 En Résumé

[TIP]
====
**Checklist Health Check** :

☑️ Vérifiez que la commande existe dans l'image de base

☑️ Si absent : installez-le dans le Dockerfile

☑️ Ou utilisez une alternative native (wget, test fichier, etc.)

☑️ Testez avec `docker exec -it container nom_commande`
====

=== Gap #3 : Localhost vs Nom de Service Docker

==== Ce qui existe actuellement

* **Chapitre 11 (reseaux.adoc)** :
** Montre les conteneurs s'appelant par nom (lignes 299-351)
** Exemple ping : `docker container run --net mynet alpine ping web`
** Explique le DNS interne Docker

==== Ce qui manque

[WARNING]
====
**Confusion critique** : Dans Docker, `localhost` ≠ nom de service.

* `localhost` = le conteneur lui-même (127.0.0.1)
* `nom_service` = un AUTRE conteneur dans le réseau Docker

**Erreur fréquente** : Configuration de logging, monitoring, proxy avec `localhost` au lieu du nom de service.

Exemple réel étudiant :
[source,yaml]
----
logging:
  driver: gelf
  options:
    gelf-address: "udp://localhost:12201"  # ❌ FAUX : localhost = conteneur actuel, pas logstash !
----

**Résultat** : Le conteneur essaie d'envoyer les logs au port 12201 de **lui-même**, échoue, et crash en boucle infinie.
====

[IMPORTANT]
====
**Correctif du 2026-09-07 : le diagnostic GELF ci-dessus est faux, et le cours a été corrigé dans l'autre sens.**

Le pilote `gelf` ne s'exécute pas dans le conteneur mais dans le **démon Docker de l'hôte**, qui n'est pas sur le réseau Compose. Mesuré sur Docker 29.7.2 / Compose v5.4.0 :

* `udp://logstash:12201` — le conteneur **ne démarre pas** : `gelf: cannot connect to GELF endpoint: logstash:12201 dial udp: lookup logstash on ...: no such host`
* `udp://localhost:12201` — le conteneur démarre et les logs partent vers le port publié de l'hôte

La recommandation « remplacer `localhost` par le nom de service » est donc à inverser pour le bloc `logging:` uniquement. Le reste de l'analyse (variables d'environnement, health checks, URL frontend) reste valable. Voir `content/chapitres/reseaux.adoc`, section « Erreur #1 », et le ticket #425.
====

== 🚨 Piège : localhost vs nom de service dans Docker

=== La Confusion Fatale

Dans un environnement **sans conteneurs**, `localhost` désigne **la machine locale**.

Dans Docker, **chaque conteneur a son propre localhost** !

[cols="2,3,3", options="header"]
|===
| Terme | Signification Hors Docker | Signification Dans Docker

| `localhost`
| La machine locale
| **Le conteneur actuel** (pas les autres !)

| `127.0.0.1`
| Interface loopback locale
| Interface loopback **du conteneur**

| `nom_service`
| (n'existe pas)
| **Un autre conteneur** dans le réseau Docker
|===

=== Exemples d'Erreurs Réelles

==== Erreur #1 : Logging GELF vers localhost

NOTE: Texte proposé non retenu en l'état — voir le correctif plus haut. La version publiée dans `reseaux.adoc` inverse le sens de cette section.

[source,yaml]
----
services:
  nginx:
    image: nginx
    logging:
      driver: gelf
      options:
        gelf-address: "udp://localhost:12201"  # ❌ FAUX !
        tag: "nginx"

  logstash:
    image: logstash
    ports:
      - "12201:12201/udp"
----

**Problème** :

* NGINX essaie d'envoyer les logs à `localhost:12201` = **lui-même**
* Logstash écoute sur **son propre** `localhost:12201` = inaccessible depuis NGINX
* Résultat : NGINX crash car il ne peut pas se connecter à son port 12201

**Solution** :

[source,yaml]
----
services:
  nginx:
    logging:
      driver: gelf
      options:
        gelf-address: "udp://logstash:12201"  # ✅ Nom du service !
----

==== Erreur #2 : Health Check avec localhost IPv6

[source,yaml]
----
services:
  webapp:
    image: tomcat:9
    healthcheck:
      test: ["CMD", "wget", "--spider", "http://localhost:8080/"]  # ⚠️ Problème IPv6
----

**Problème subtil** :

* `localhost` peut résoudre vers `::1` (IPv6) ou `127.0.0.1` (IPv4)
* Tomcat écoute parfois SEULEMENT sur IPv4
* Health check essaie IPv6 → échoue

**Solution** :

[source,yaml]
----
healthcheck:
  test: ["CMD", "wget", "--spider", "http://127.0.0.1:8080/"]  # ✅ Force IPv4
----

==== Erreur #3 : Backend URL avec localhost

[source,yaml]
----
services:
  frontend:
    environment:
      API_URL: "http://localhost:5000"  # ❌ FAUX dans frontend !

  backend:
    ports:
      - "5000:5000"
----

**Problème** :

* Frontend essaie d'appeler `http://localhost:5000`
* `localhost` dans frontend = le conteneur frontend lui-même
* Backend n'est PAS sur localhost du frontend !

**Solutions possibles** :

[source,yaml]
----
# Solution 1 : Appel depuis le navigateur (client-side)
frontend:
  environment:
    API_URL: "http://localhost:5000"  # ✅ Navigateur → hôte Docker → backend

# Solution 2 : Appel depuis le frontend (server-side)
frontend:
  environment:
    API_URL: "http://backend:5000"  # ✅ Frontend → réseau Docker → backend
----

=== Tableau de Référence

[cols="3,2,3", options="header"]
|===
| Contexte | Utilisez | Exemple

| Service A appelle service B (même réseau)
| **Nom du service B**
| `http://backend:5000`

| Health check d'un service sur lui-même
| `localhost` ou `127.0.0.1`
| `http://127.0.0.1:8080`

| Logging vers un autre service
| **Nom du service**
| `gelf-address: "udp://logstash:12201"`

| Port exposé accessible depuis l'hôte
| `localhost` (sur l'hôte)
| `curl http://localhost:8080`

| Configuration réseau interne
| **Nom du service**
| `REDIS_URL: redis://cache:6379`
|===

=== Règle Mnémotechnique

[TIP]
====
**"localhost" dans Docker = "moi-même"**

Si vous voulez parler à **un autre conteneur**, utilisez **son nom de service**.

Si vous voulez parler à **vous-même** (votre propre conteneur), utilisez `localhost`.
====

=== 🎓 Exercice Pratique

Créez deux services :

[source,yaml]
----
services:
  web:
    image: nginx
    networks:
      - mynet

  api:
    image: httpbin/httpbin
    networks:
      - mynet

networks:
  mynet:
----

Depuis `web`, essayez :

1. `curl http://localhost/get` → Qui répond ?
2. `curl http://api/get` → Qui répond ?
3. Comprenez la différence !

=== 📊 En Résumé

[IMPORTANT]
====
**Deux environnements réseau distincts** :

1. **Réseau hôte** (votre machine) : `localhost` = votre PC
2. **Réseau Docker** (conteneurs) :
   * `localhost` = le conteneur actuel
   * `nom_service` = un autre conteneur
====

+

====
Pour une accessibilité maximale, envisagez de migrer ce projet vers GitHub/GitLab.com public pour les étudiants hors Université d'Artois.
====
2. Lancez : `docker compose up -d`
3. Observez les échecs : `docker ps` montre "Created" ou "unhealthy"
4. **Diagnostiquez** chaque problème :
   * Utilisez `docker logs nginx`
   * Utilisez `docker inspect nginx`
   * Utilisez `docker events`
5. **Corrigez** les 3 erreurs
6. Vérifiez : `curl http://localhost/` doit fonctionner
